# Android IPC, intents and permissions

Audit the merged manifest plus entry-point code. Trace untrusted data from receipt to privileged operation; preserve intentional public deep links and launcher entries instead of making every component private.

## Component / intent boundaries
- Mark private components non-exported. Protect private family-app IPC with declared signature permissions (or supported knownSigner certificates). Public integrations need explicit validation and their own authorization design.
- Validate incoming intents in both onCreate and onNewIntent; update the Activity's current intent only consistently with validated processing. Never forward a nested untrusted Intent directly. Either reconstruct a minimal intent, or: null its `selector`, strip `FLAG_GRANT_*_URI_PERMISSION` flags, `resolveActivity()` and require **both** `packageName` and `className` to match an allowlist, then pin `component` to the resolved target. Or use `IntentSanitizer` (no `allowFlags()` → all grant flags rejected; catch `SecurityException` and `BadParcelableException`; it doesn't enforce extra presence, check that yourself). A matching package or exported destination alone is insufficient authorization.
- Prefer immutable PendingIntents. Where mutability is necessary, constrain the target and permitted operation; never issue a mutable implicit token.
- Exported bound services: expose a cross-process interface (AIDL `Stub` or `Messenger`), not a local `Binder` subclass. In an active Binder transaction (`Stub` method / `onTransact()`, or `Message.sendingUid`), authenticate UID and signing certificates; treat `callingUid == Process.myUid()` as **reject** (it means no active IPC or identity already cleared), and enforce read/write permissions at the relevant method before clearing identity or switching threads. Do not use caller-provided package extras. `Binder.getCallingUid()` in Service.onBind, Activity callbacks or BroadcastReceiver.onReceive does not authenticate the original remote caller; use manifest protection or supported sender APIs there.
- Protect broadcasts with permissions/explicit targets and correct exported receiver flags; distinguish protected system broadcasts from custom actions. Verify compatibility permission declarations in the merged manifest for older AndroidX receiver implementations. Never authenticate a sender with `PendingIntent.getCreatorPackage()`/`getCreatorUid()` — any app holding a trusted app's PendingIntent can attach it. Pre-API 34: protect the receiver with a `signature` (or `signature|knownSigner`, API 31+) permission; below minSdk 31 use a bound Service/Provider and verify `Binder.getCallingUid()`. API 34 sender identity can be absent and must fail closed for protected operations.
- For providers, separate read/write authorization, allowlist URI paths/projections and parameterize selection values. Grant only required URI/modes; revoke temporary grants with `revokeUriPermission(targetPackage, uri, modes)` on API 26+ (fallback: the two-argument form), and `releasePersistableUriPermission` when durable access ends. `grantUriPermissions=true` allows grants for the provider broadly; do not claim that child path declarations alone narrow that setting. To constrain grantable paths, verify the documented false-plus-specific-path configuration and actual FileProvider behavior.

## Runtime permissions
Request only permissions required at the point of use. Prefer Photo Picker for user-selected media. Request foreground location before background location and retain coarse-only functionality where possible.

Recheck the grant before protected operations and catch SecurityException for revocation races. Use Activity Result APIs; when `shouldShowRequestPermissionRationale` is true, show the rationale dialog and launch the request only from its Continue action; handle denial gracefully. A false `shouldShowRequestPermissionRationale` also occurs before the first request: combine with request history/result instead of immediately declaring permanent denial. Offer settings recovery when justified; avoid prompt loops.

Test unauthorized IPC, spoofed identity, nested-intent redirects, warm Activity launches, provider read/write separation, URI grants and runtime revocation. Report concrete affected entry points and evidence; do not call a static review a complete security certification.
