# Connection and REST fallback

- No tools: report a discovery/transport issue. Test a harmless search only when a search tool is available, before diagnosing OAuth. 401: check credentials or reconnect through host. 403: check API enablement, scopes, IAM, quota project and `serviceusage.services.use`. 429 on answer: search, not OAuth reset.
- Repeated expiry: inspect offline grant (`access_type=offline`, renewed consent when necessary), secure refresh-token persistence, revoked grants and `invalid_grant`. External/Testing consent may limit refresh-token lifetime. CLI auth and ADC are separate.
- Host-managed OAuth cannot be repaired by skill text or a Node dependency. For a backend you own, follow [Google OAuth web-server guide](https://developers.google.com/identity/protocols/oauth2/web-server) and [Google Auth Library](https://github.com/googleapis/google-auth-library-nodejs); preserve existing refresh tokens when absent from new responses. Never log tokens.
- REST only with existing authorized access: [quickstart](https://developers.google.com/knowledge/quickstart), [REST reference](https://developers.google.com/knowledge/reference/rest). Use supported OAuth or restricted API-key header; explicit quota project where needed. `GET /v1/documents:searchDocumentChunks`, `GET /v1/documents:batchGet` (repeated `names`, no JSON body), `POST /v1:answerQuery`. Check live schema and upstream [attribution guidance](https://github.com/google/skills/tree/main/skills/developers/retrieving-developer-knowledge/references) when using direct REST.
- If MCP and authorized REST are unavailable, use public official Google docs and disclose the fallback. No implicit installation, API enablement, login, credential creation or permission expansion.
